## 1. 最高原则：三条架构红线

设计文档里的三条不可推翻决策，翻译成架构约束：

**① 网络出口单点收敛**

整个插件族里，**只有 `dsh-social-cloud` 一个包碰网络**。其他包一律不许发请求。

它的 `publish()` 只接受带用户确认标记的卡片对象。代码审查时只需要盯这一个文件，就能回答"会不会偷偷上传用户对话"。

**② 摘要生成用用户自己的模型**

调 `ctx.llm`（用户自己配的 DeepSeek API key），**原始对话从头到尾不出本机**。

你的服务端只收到已经过审的卡片正文。这不是策略，是数据流上的物理隔离——你想看也看不到。

**③ 服务端与 harness 解耦**

harness 层只做两件事：**采集上下文、渲染 UI**。
隐私逻辑、身份系统、观点池、匹配算法全在服务端，通过一层薄 HTTP 接口通信。

将来换宿主或自建 App，重写的只有最外面那层壳。

## 2. 包拆分

按 DSH 的 seam 约定（Definition / Provider / Consumer）拆：

```
packages/social/
├── dsh-social/              [Service Definition]  类型 + 抽象服务，零依赖
├── dsh-social-cloud/        [Service Provider]    ★唯一有网络权限
├── dsh-social-local/        [Service Provider]    本地 mock，阶段 0 与开发用
├── dsh-social-curator/      [Consumer]            观察对话、判断时机、生成草稿
├── dsh-social-commands/     [Consumer]            用户动作（发布/撤回/加入）
└── dsh-social-client/       [Client Plugin]       Conversation Node + React 渲染
```

**为什么这么拆：**

- `local` / `cloud` 两个 provider 同接口，`cordis.yml` 换一行就切换。**阶段 0 完全可以只装 local**，不需要服务端就能测转化率。
- `curator` 是唯一消耗 token 的包，必须能被用户单独关掉。
- `client` 必须是独立包——它需要在 `package.json` 声明 `dsh.client` 才会被扫描到。

**依赖方向**（provider 与 consumer 互不依赖，这是 seam 的要点）：

```
        dsh-social  (definition)
        ▲    ▲    ▲
        │    │    │
   cloud┘  curator└commands        client ──(仅类型导入)──▶ dsh-social
   local┘
```

## 3. Service Definition

```ts
// packages/social/dsh-social/src/index.ts
import { Service, type Context } from '@deepseek-ai/cordis'
import type { Branded } from '@deepseek-ai/dsh-brand'

declare module '@deepseek-ai/cordis' {
  interface Context {
    social: SocialService
  }
}

export type CardId = Branded<'CardId'>
export type ThreadId = Branded<'ThreadId'>

/** 观点卡片——发布的唯一单位。刻意不含任何原始对话文本。 */
export interface OpinionCard {
  readonly id: CardId
  /** AI 生成、用户过审后的观点正文。已剥离处境细节。 */
  readonly claim: string
  /** 支撑理由，可选。 */
  readonly reasoning?: string
  /** 话题向量，本地算好再上传；服务端不做二次抽取。 */
  readonly topicVector: readonly number[]
  readonly createdAt: number
  /** 用户已过审的证明。publish() 拒绝 false。 */
  readonly userApproved: boolean
}

/** 草稿：AI 提议但用户尚未确认。永不出本机。 */
export interface CardDraft {
  readonly draftId: string
  readonly claim: string
  readonly reasoning?: string
  /** 本地自评的隐私风险，仅用于 UI 提示排序，不做拦截。 */
  readonly riskHint: 'low' | 'medium' | 'high'
}

export abstract class SocialService extends Service {
  constructor(ctx: Context) {
    super(ctx, 'social')
  }

  /** 发布一张已过审的卡片。userApproved !== true 时必须抛错。 */
  abstract publish(card: OpinionCard): Promise<CardId>

  /** 撤回。必须真删，不是隐藏。 */
  abstract retract(id: CardId): Promise<void>

  /**
   * 按话题向量拉相关卡片。
   * 服务端负责 k-匿名门槛过滤（不足 N 人的话题直接不返回）。
   */
  abstract relevant(vector: readonly number[], limit: number): Promise<OpinionCard[]>
}
```

**注意 `userApproved` 这个字段。** 它看起来冗余（反正只有用户点了才会调 publish），但把它放进类型里，就让"未过审的东西被发出去"变成一个编译期 + 运行期都挡得住的错误，而不是靠开发者记性。

## 4. 数据流：从对话到卡片

### 4.1 完整链路

```
用户与 AI 正常对话
        │
        │  ctx.on('session/event')  —— curator 被动观察，不干预
        ▼
    turn/end 到达
        │
        │  判断：这一轮值不值得提议？（本地启发式，不花钱）
        │  · 轮次长度够不够
        │  · 是不是判断性话题（而非"帮我改这段代码"）
        │  · 距离上次提议是否太近（节流）
        ▼
    值得 ──▶ ctx.jobs 后台任务
        │        │  调 ctx.llm 生成 CardDraft
        │        │  （用户自己的 key，不出本机）
        │        ▼
        │    emit 自定义 session 事件 'social/draft'
        │        │
        │        ▼
        │    ★ 客户端渲染一张卡片，带 [发布] [改一下] [不用了]
        │        │
        │        ▼ 用户点「发布」
        │    ctx.commands 分派（无需模型轮次）
        │        │
        │        ▼
        │    ctx.social.publish(card)  ──▶ dsh-social-cloud ──▶ 服务端
        │        │
        │        ▼
        │    emit 'social/published'，节点状态更新为已发布
        │
    不值得 ──▶ 什么都不做（默认路径，绝大多数轮次走这里）
```

### 4.2 三个关键判断

**① 为什么监听 `turn/end` 而不是每条消息**

对话进行中打断是设计文档明确否掉的。轮次结束是用户天然的停顿点，也是内容完整的时刻。

**② 为什么走 `ctx.jobs` 后台**

摘要生成要调一次 LLM，几秒钟。放在主链路上会让用户觉得"AI 卡住了"。后台跑完再冒出卡片，用户无感。

**③ 为什么用 `ctx.commands` 而不是让模型调工具**

这条最重要。「发布」是**用户的动作，不是模型的动作**。

如果做成模型可调用的 tool，就意味着模型可以自己决定发布——这直接违反"发出前必须用户过审"。用 `ctx.commands`（文档明确说明"无需模型轮次即可分派"），发布路径根本不经过模型，也就不存在模型被诱导发布的可能。

**架构上把危险动作放在模型够不到的地方，比在 prompt 里叮嘱它可靠得多。**

## 5. 会话事件设计

按不变式要求，新增持久事实必须扩展 `SessionEventMap`：

```ts
// packages/social/dsh-social/src/events.ts
declare module '@deepseek-ai/dsh-session/types' {
  interface SessionEventMap {
    /**
     * AI 提议了一张草稿卡片。仅本地，永不上传。
     * @mode emit
     */
    'social/draft': {
      readonly draftId: string
      readonly turn: number
      readonly step: number
      readonly claim: string
      readonly reasoning?: string
      readonly riskHint: 'low' | 'medium' | 'high'
    }

    /**
     * 用户对草稿做出了决定。
     * @mode emit
     */
    'social/decision': {
      readonly draftId: string
      readonly turn: number
      readonly step: number
      readonly decision: 'published' | 'edited' | 'discarded'
      /** 仅 published 时存在。 */
      readonly cardId?: string
    }
  }
}
```

**`social/decision` 是阶段 0 那个转化率指标的数据源。** 它落在会话日志里，可以直接统计"提议了多少次、发布了多少次"——不需要额外埋点，也不需要上传任何东西。

**注意 `turn` / `step` 坐标是必需的**：Conversation Node 靠它定位渲染位置。

## 6. UI：Conversation Node

Client 插件独立打包，`package.json` 里声明：

```json
{
  "name": "@you/dsh-social-client",
  "dsh": { "client": { "platform": "web" } },
  "exports": { "./client": "./dist/client.js" }
}
```

Node 定义遵循 Cookbook 的模式——`match` 只做身份提取，`start` / `update` 增量构造状态：

```ts
const draftDefinition: ConversationNodeDefinition<DraftState> = {
  kind: 'social-draft',
  target: 'chat',

  // 身份提取器：只看当前事件，返回业务 id + 生命周期角色
  match: (event) => {
    if (event.type === 'social/draft') {
      return { id: event.data.draftId, role: 'start' }
    }
    if (event.type === 'social/decision') {
      return { id: event.data.draftId, role: 'update' }
    }
    return null
  },

  start: (_ctx, match) => {
    if (match.event.type !== 'social/draft') throw new Error('need social/draft')
    const d = match.event.data
    return {
      turn: d.turn, step: d.step,
      claim: d.claim, reasoning: d.reasoning,
      riskHint: d.riskHint,
      status: 'pending' as const,
    }
  },

  update: (ctx, match) => {
    if (match.event.type !== 'social/decision') return ctx.state
    return { ...ctx.state, status: match.event.data.decision }
  },

  publication: 'immediate',

  buildViewNode: (ctx) => ctx.state === undefined ? null : {
    key: ctx.key,
    kind: 'social-draft',
    id: ctx.id,
    target: 'chat',
    anchorSeq: ctx.start?.event.seq ?? 0,
    location: ctx.start?.location ?? { kind: 'unresolved' },
    visibility: 'visible',
    data: viewData(ctx.state),
  },
}
```

**已决定的 UI 行为：**

- 草稿卡片渲染在对话流内，不做常驻侧栏（设计文档 5.2）
- 用户做出决定后节点**不消失**，改为收起的一行状态（Cookbook 明确要求：已发布的 node 要保持同一个 key，需要隐藏用 `visibility: 'hidden'`，不能返回 `null` 撤回）
- 推荐卡片同理，走另一个 `kind: 'social-suggestion'`，且**数据不足时整个不渲染**

## 7. 一个关键决定：推荐内容不进模型上下文

阶段 1 里，别人的观点卡片**只渲染给用户看，不通过 `agent.inject()` 进模型上下文**。

理由三条：

1. **隐私**：一旦注入，别人的观点就被写进你的会话日志，持久化在你本机
2. **不变式负担**：模型可见即已记录，注入就必须新增会话事件族，复杂度陡增
3. **打断**：用户在干活，AI 主动引用陌生人的观点是噪音

代价是 AI 不知道旁边有这些卡片，没法说"隔壁那个观点你可以看看"。**这个代价值得付。**

> **分界线**：阶段 4 的房间模式必须走 `agent.inject()`——AI 要主持讨论，就必须看得见所有人的发言。所以房间是第一个需要处理不变式的功能，这也是把它排在最后的技术原因。

## 8. 服务端接口契约

只定接口，不定实现——保证 harness 层可以先跑起来。

```
POST   /v1/cards              发布卡片
       body: { claim, reasoning?, topicVector, ephemeralId }
       resp: { cardId }

DELETE /v1/cards/{cardId}     撤回（真删，非隐藏）
       resp: 204

POST   /v1/cards/relevant     拉相关卡片
       body: { topicVector, limit }
       resp: { cards: [{ cardId, claim, reasoning?, threadId? }] }
       ★ 服务端负责 k-匿名过滤：命中人数 < N 的话题直接不返回

POST   /v1/threads            对某张卡片发起匿名回复
       body: { cardId, ephemeralId, text }        [阶段 2]

POST   /v1/rooms              由卡片升级为房间                [阶段 4]
```

**契约上的四条硬约束：**

| 约束 | 落地方式 |
|---|---|
| 服务端不存对话索引 | 接口里根本没有"上传对话"这个 endpoint。想存也没有输入 |
| 卡片按引用渲染 | 推荐接口返回 `cardId`，客户端渲染时按 id 取。删除后所有引用同时失效 |
| k-匿名门槛 | 服务端实现，客户端拿不到不足门槛的数据 |
| 封禁绑真实 user_id | `ephemeralId` 与 `realUserId` 的映射只在服务端。客户端永远看不到 |

**认证**：用 `ctx.credentials` 存 token，不要自己写文件。

**`ephemeralId` 由谁生成**：客户端每个 thread 生成一次，服务端记录映射。客户端生成是为了让"一次性"这件事对用户可验证。

## 9. 动手前必须先验的两件事

这两个不确定项会影响整个交互设计，建议第一天就写个最小 demo 打通。

**① UI 按钮能不能直接触发 `ctx.commands`？**

文档说 `ctx.commands` "无需模型轮次即可分派"，但没写清楚 Web Client 里的一个 React 按钮怎么调到它。

可能路径：client 插件 → HTTP 打到 `dsh-host-webserver` 注册的前缀路由 → 服务端侧插件 → `ctx.commands`。

**如果这条路不通，整个"用户点击发布"的模型就要重设计**，所以必须先验。

**② 后台 LLM 调用的正确姿势**

`ctx.jobs` 是给"模型可调用的后台任务"用的，还是插件也能自己起？摘要生成不能占用用户当前的 agent turn，也不能阻塞。

同时要确认：这次调用的 token 计费会不会算进用户当前会话的 token 计量（`ctx.tokenMeter`）——如果会，用户看到 token 莫名上涨会立刻卸载插件。

**保底方案**：如果两条都不顺，阶段 0 完全可以退化成一个 `/social-draft` 手动命令——用户自己敲，AI 生成草稿。虽然丢掉了"AI 主动提议"这个核心杠杆，但足够验证转化率的下限。

## 10. 落地顺序

| 步骤 | 产出 | 目的 |
|---|---|---|
| 1 | scratch-plugin 跑通 `--patch` 加载 | 打通开发链路 |
| 2 | 监听 `session/event`，控制台打印 turn 边界 | 验证事件钩子 |
| 3 | 手动命令触发草稿生成 | 绕开不确定项 ①，先验 LLM 调用 |
| 4 | Conversation Node 渲染草稿卡片 | 验证 UI 扩展（最不熟的部分） |
| 5 | 按钮 → 命令链路 | 验证不确定项 ① |
| 6 | `dsh-social-local` 落盘 mock | 端到端跑通，**此时即可开始测转化率** |
| 7 | 换 `dsh-social-cloud` | 接真实服务端 |

**第 6 步是第一个有价值的里程碑**——不需要服务端、不需要第二个用户，就能拿到设计文档里那个生死线数字。
